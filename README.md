# bench.js — простой бенчмарк скорости загрузки
Консольный скрипт на Node.js (без зависимостей): делает N последовательных
запросов к заданному URL, дожидается полного ответа на каждый, выводит
время запроса и среднюю скорость скачивания.

Первый из запросов всегда будет самым долгим в рамках одного запуска из-за установки TCP-соединения и TLS-рукопожатия.

## Требования
* Node.js 20.3+ (используется встроенный `fetch` и `AbortSignal.timeout`).

## Запуск

```bash
node bench.js <url> [количество] [интервал(мс)]
```

### Аргументы
* `url` *(обязательный)* — полный адрес ресурса (`http://` или `https://`).
* `количество` *(опционально, по умолчанию `10`)* — количество последовательных запросов (целое число `>= 1`).
* `интервал` *(опционально, по умолчанию `500`)* — пауза между запросами в миллисекундах (целое число `>= 0`).

### Примеры
```bash
# 10 запросов с интервалом 500 мс (значения по умолчанию)
node bench.js https://example.com

# 5 запросов с паузой 1 секунда (1000 мс)
node bench.js https://example.com 5 1000
```

## Единицы измерения и методика расчёта
* **Время запроса:** миллисекунды (`мс`). Пауза между запросами (`intervalMs`) не включается в замер времени скачивания.
* **Объём данных:** автоматический выбор двоичных единиц (`байт`, `КБ`, `МБ`, `ГБ` с шагом `1024`).
* **Скорость скачивания:** `байт/с`, `КБ/с`, `МБ/с` или `ГБ/с` (рассчитывается как отношение общего объёма скачанных данных к суммарному чистому времени всех запросов).

## Что считается
- Объём берётся из размера полученного тела ответа (`byteLength` распакованного ответа),
  а не из заголовка `Content-Length` — так скрипт корректен для сжатых и
  «чанковых» ответов. Для сжатых ответов это объём контента, не сетевой трафик.
- Замер включает время на handshake, получение заголовков и парсинг тела ответа.

## Что бы я улучшил, будь у меня больше времени?

Если заложить больше времени и внимательнее изучить детали задачи, бизнес-процесс и назначение
(какую конкретную проблему нужно решить — ведь таким образом я могу детальнее понять непосредственно 
технические требования и реализацию):

- Разделил бы сетевые ошибки и таймауты.
- Алиасы импорта.
- Jitter, например, для `429 Too Many Requests`.
- Фабричный метод — в принципе не нужен на данном этапе, но если мы предполагаем, что проект будет жить годами, а бизнес-процесс усложняться, нагружая модули зависимостями — не помешает.
- Более внимательно изучил бы инварианты на инстанцирование, впрочем — сейчас сервис прост и процессы не сложные.
- Добавил бы другую реализацию HTTP-клиента через адаптер для контроля над `Keep-Alive`.
- `response.body` stream для больших объёмов файлов, если в модуле понадобится TTFB мерить.
- Более агрессивный способ обхода кеширования через рандомный query-параметр (опционально).
- Красивый вывод в консоль параллельно файл-логгеру, например при настройке, что это необходимо.
- `SIGINT` / `SIGTERM`.
- Юнит-тесты (обязательно).
